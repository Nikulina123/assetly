# Assetly Inventory — Backend API Implementation Plan

## Endpoint

```
POST /api/v1/inventory/checkin
Content-Type: application/json
```

Single endpoint — receives one check-in submission, persists it, and returns confirmation.

---

## Payload Fields

### User-submitted (from GUI form)

| Field | Type | Description |
|---|---|---|
| `first_name` | `string` | Employee's first name — links the device to a person |
| `last_name` | `string` | Employee's last name — used for display and search |
| `email` | `string` | Employee's work email — used to send confirmation and to deduplicate person records |
| `project` | `string (enum)` | Which project the employee is assigned to — used for project-level device reporting |

### Hardware (collected automatically)

| Field | Type | Description |
|---|---|---|
| `timestamp` | `string (ISO-8601)` | Local time when data was collected on the device — used to detect stale/queued submissions |
| `hostname` | `string` | Machine network name — used to identify the device on the network |
| `ip_address` | `string` | IP at time of check-in — useful for network auditing, not for permanent identification |
| `brand` | `string` | Manufacturer (Apple, Dell, Lenovo…) — used for fleet composition reports |
| `model` | `string` | Device model name — used for warranty lookups and procurement planning |
| `serial_number` | `string` | Hardware serial — **primary device identifier**, used for deduplication and tracking |
| `cpu` | `string` | Processor name and speed — used for performance tier classification |
| `ram` | `string` | Total RAM rounded to GB — used to flag under-spec devices |
| `storage` | `string` | Disk size (and model on Windows) — used for capacity planning |
| `os` | `string` | OS name and version — used to track outdated systems and compliance |

### Suggested new fields to add

| Field | Type | Source | Description |
|---|---|---|---|
| `platform` | `string (enum: windows, macos, linux)` | Derived from agent | Enables platform-split reports without parsing the `os` string |
| `agent_version` | `string` | Hardcoded in agent | Tracks which version of the agent submitted — useful when rolling out updates |
| `submission_type` | `string (enum: online, queued)` | Agent logic | Whether it was submitted live or flushed from the offline queue — helps detect connectivity issues |
| `checkin_id` | `string (UUID)` | Generated by agent before POST | Idempotency key — if the agent retries after a network error, the backend can deduplicate |
| `os_version` | `string` | Parsed from `os` field | Separate normalized version string for filtering (e.g. `"14.4.1"` vs `"macOS 14.4.1"`) |

## Database Schema (suggested table: `device_checkins`)

```sql
CREATE TABLE device_checkins (
    id               SERIAL PRIMARY KEY,
    checkin_id       UUID UNIQUE NOT NULL,          -- idempotency key
    received_at      TIMESTAMPTZ DEFAULT NOW(),     -- server-side timestamp
    timestamp        TIMESTAMPTZ NOT NULL,          -- client-reported collection time

    -- Person
    first_name       TEXT NOT NULL,
    last_name        TEXT NOT NULL,
    email            TEXT NOT NULL,
    project          TEXT NOT NULL,

    -- Device identity
    serial_number    TEXT NOT NULL,
    hostname         TEXT NOT NULL,
    brand            TEXT NOT NULL,
    model            TEXT NOT NULL,

    -- Hardware specs
    cpu              TEXT,
    ram              TEXT,
    storage          TEXT,
    ip_address       TEXT,

    -- OS
    os               TEXT NOT NULL,
    os_version       TEXT,
    platform         TEXT,

    -- Agent metadata
    agent_version    TEXT,
    submission_type  TEXT DEFAULT 'online'
);
```

> Index on `serial_number`, `email`, `project`, `platform`, `received_at` — these are the filter axes.

## Endpoint Behaviour

```
POST /api/v1/inventory/checkin

→ 200 OK             { "status": "ok", "id": "<checkin_id>" }
→ 409 Conflict       { "status": "duplicate" }            (checkin_id already exists)
→ 422 Unprocessable  { "status": "error", "errors": [...] }
```

**Processing steps:**
1. Validate required fields (`first_name`, `last_name`, `email`, `serial_number`, `timestamp`)
2. Check `checkin_id` uniqueness — return `409` if duplicate (handles agent retries)
3. Normalize `os` → derive `platform` + `os_version` if not sent by agent
4. Persist to `device_checkins`
5. Optionally upsert a `devices` table keyed on `serial_number` with latest known state
6. Return `{ "status": "ok", "id": "<checkin_id>" }`

## Useful Filters

### By identity

| Filter | Use case |
|---|---|
| `serial_number` | Look up full history of one device |
| `email` | Find all devices owned by one person |
| `hostname` | Quick lookup by machine name |

### By fleet slice

| Filter | Use case |
|---|---|
| `project` | Which devices does project X use |
| `platform` | Windows vs macOS vs Linux split |
| `brand` / `model` | Find all MacBook Pro 14" for warranty batch |
| `os_version` | Identify machines still on an old OS — compliance |

### By time

| Filter | Use case |
|---|---|
| `received_at` range | Devices that checked in within a period |
| `received_at` — absence | Devices that have NOT checked in within the company's configured check-in interval (overdue) |
| `submission_type = queued` | Devices that were offline during check-in |

### By spec / compliance

| Filter | Use case |
|---|---|
| `ram LIKE "8 GB"` | Flag under-spec devices |
| `os_version < "14"` | Find outdated macOS fleet |
| `platform = windows` + `os LIKE "%10%"` | Windows 10 deprecation audit |

## Agent Updates Required

To support the new fields, add these to the payload in both agents before the POST.

**Python (`inventory_agent.py`):**
```python
import uuid
payload = {
    **user_data, **hw,
    "checkin_id":      str(uuid.uuid4()),
    "agent_version":   "2.0",
    "submission_type": "online",   # set to "queued" when flushing from queue
    "platform":        _sys.lower(),  # "darwin" → "macos", "linux", "windows"
}
```

**PowerShell (`AssetlyAgent_Windows.ps1`):**
```powershell
$payload["checkin_id"]      = [guid]::NewGuid().ToString()
$payload["agent_version"]   = "1.0"
$payload["submission_type"] = "online"
$payload["platform"]        = "windows"
```

## Deploy ordering (hard gate)

Migrations **013** (`rate_limit_hits`) and **014** must be applied to the
production database with `psql -1 <migration file>` **before** deploying any
code that depends on them. This is not merely recommended ordering — it is a
hard gate:

- Code from Task 6 onward calls `enforce_rate_limit` on `/admin/login`,
  `/api/v1/enroll`, `/checkin`, `/config`, and `/agent/manifest`, all of which
  hit the `rate_limit_hits` table added by migration 013.
- `check_rate_limit` (`backend/app/rate_limit.py`) catches
  `asyncpg.UndefinedTableError` specifically and fails **open** (allows the
  request, logs at ERROR) so a missed migration degrades to "no rate limiting"
  rather than a 500 on every gated route — but that is a safety net for an
  ordering mistake, not a substitute for the correct order. Deploy the
  migration first regardless.
- Migration 014's consumers already catch broadly and degrade quietly by
  design; treat 013 and 014 as a single ordered pair applied ahead of the code
  that uses them, not as independently orderable.

Sequence for any deploy that includes new or changed migrations:

```
psql -1 -f backend/migrations/013_rate_limit.sql "$DATABASE_URL"
psql -1 -f backend/migrations/014_auth_failure_digest.sql "$DATABASE_URL"
# only then deploy/promote the new application code
```

## Required production environment

Required in production: `ENVIRONMENT=production` and `SESSION_COOKIE_SECURE=true`.
The application refuses to start without the second when the first is set.

## Device lifecycle

**Hardware replacement.** A device credential is bound to its enrolled serial.
When a machine's board or chassis is replaced and its serial changes, its
check-ins will be rejected with 409. The fix is admin-initiated: revoke the old
credential in the portal, then re-run the installer on the machine. This is
deliberately not self-service — an endpoint that could rebind its own
credential would reopen exactly the hole the binding closes.
